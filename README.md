# CNN-DATA-BOT

Бот на Node.js (mineflayer) для Linux-сервера. Заходит на ваниль-сервер, переходит в spectator, следит за игроком через `/spectate` и пишет мир вокруг него в куб `size × size × size` (по умолчанию 48³).

Запись устроена как **один ключевой кадр в начале и дальше только изменения**. Полные кадры собираются потом, когда понадобятся (`tools/rebuild.py`). Снимков по таймеру нет.

Для каждого игрока отдельный набор файлов. Когда игрок выходит, запись закрывается и бот переключается на следующего. Версия Minecraft пишется в метаданные.

## Требования

- Linux, Node.js 18+
- Для чтения записей: Python 3 и numpy

## Установка

```bash
cd CNN-DATA-BOT
npm install
cp config.example.json config.json   # поправь host/port/size
node index.js
```

В консоли сервера выдай боту op: `op CNN_DATA_BOT`. Дальше он сам делает `/gamemode spectator` и `/spectate <ник>`.

Настройки можно переопределить переменными окружения: `CNN_HOST`, `CNN_PORT`, `CNN_USERNAME`, `CNN_VERSION`.


## Управление

Через терминал (если запущен вручную) или через FIFO `control.fifo` (работает и под systemd):

```bash
echo Steve > control.fifo     # переключиться на игрока
echo list > control.fifo      # кто онлайн (ответ в логе)
echo auto > control.fifo      # снова брать первого попавшегося
echo status > control.fifo    # состояние записи
echo quit > control.fifo      # выйти
```

Если ник не указан, бот берёт первого игрока из списка.

## Настройки (`config.json`)

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `host`, `port` | localhost, 25565 | сервер |
| `username` | CNN_DATA_BOT | ник бота |
| `version` | false | версия Minecraft, false = автоопределение |
| `size` | 48 | сторона куба (±size/2 вокруг бота) |
| `gzipLevel` | 3 | 1 быстрее, 9 меньше файл |
| `outDir` | data | папка записей |
| `controlFifo` | control.fifo | путь к FIFO |
| `metaEverySec` | 10 | как часто обновлять `.json` во время записи |
| `readyTimeoutSec` | 15 | сколько ждать, пока бот прилипнет к игроку, прежде чем начать запись |

## Как записывается

1. Бот ждёт, пока `/spectate` сработает и он окажется рядом с игроком. Затем начинается тик 0 (тик = 50 мс).
2. **Ключевой кадр:** все секции мира 16×16×16, которые пересекает куб, записываются целиком.
3. **Дальше только изменения:**
   - изменение блока внутри отслеживаемых секций, 19 Б на блок;
   - сдвиг куба вслед за ботом, 17 Б;
   - когда куб заходит в новую секцию, она пишется целиком, а секция, из которой вышли, закрывается;
   - сущности: сначала полный список, потом только изменившиеся и исчезнувшие.
4. Каждый блок куба всегда лежит в отслеживаемой секции, поэтому кадр на любой тик можно собрать без дополнительных данных.

Если чанк ещё не загружен, секция ждёт и пишется, как только он придёт. Если сервер повторно прислал чанк, секции этого чанка пишутся заново поверх.

## Файлы

На каждую запись три файла:

- `ник_время.blocks.bin.gz` — блоки (ключевой кадр и изменения)
- `ник_время.entities.jsonl.gz` — сущности (ключевой кадр и изменения)
- `ник_время.json` — метаданные: версия, палитры, счётчики

### Метаданные (`.json`)

| Поле | Что внутри |
|---|---|
| `version` | `minecraft` (например `1.20.4`), `protocol`, `dataVersion`, `majorVersion` |
| `size`, `tickMs`, `ticks`, `startedAt`, `player` | параметры записи |
| `world` | `minY` и `height` мира |
| `palette` | `stateId → { name, props }` для встреченных блоков |
| `entityTypes` | `typeId → { name, category, width, height }` |
| `items` | `itemId → { name }` |
| `counts` | сколько секций, изменений блоков и т.п. записано |

`stateId` учитывает состояние блока (ориентацию, уровень воды и т.д.). `0` — воздух, `65535` — неизвестно (чанк не был загружен).

### Блоки (`.blocks.bin.gz`)

Поток записей подряд, little-endian. Заголовок у всех 17 байт: `u8 тип, u32 тик, i32 a, i32 b, i32 c`.

| Тип | Что | a, b, c | Данные после заголовка |
|---|---|---|---|
| 1 `SECTION` | полный кадр секции | координаты секции | 4096 × u16, индекс `(y*16+z)*16+x` |
| 2 `BLOCK` | изменение блока | координаты блока | u16 stateId |
| 3 `ORIGIN` | куб сдвинулся | угол куба x0, y0, z0 | нет |
| 4 `DROP` | секцию больше не отслеживаем | координаты секции | нет |

Записи идут в порядке тиков.

### Сущности (`.entities.jsonl.gz`)

JSON Lines. Строка пишется только в тик, где что-то изменилось.

```json
{"t":0,"full":1,"tg":42,"upd":[{"id":42,"type":128,"pos":[124.5,84,-15.5],"vel":[0,0,0],"yaw":1.57,"pitch":0.1,"head":1.57,"ground":1,"name":"Steve","hp":20,"held":[802,1]}]}
{"t":3,"upd":[{"id":42,"type":128,"pos":[124.9,84,-15.5], "...": "..."}]}
{"t":4,"upd":[],"del":[57]}
```

| Поле | Смысл |
|---|---|
| `t` | тик |
| `full` | 1 = полный список (первая строка), перед применением список очищается |
| `tg` | ID сущности игрока, за которым следит бот (пишется в начале и при смене) |
| `upd` | новые и изменившиеся сущности (целиком, не по полям) |
| `del` | ID сущностей, которые исчезли или вышли из куба |
| `id`, `type` | ID на сервере и ID типа (→ `entityTypes`) |
| `pos`, `vel` | позиция и скорость |
| `yaw`, `pitch`, `head` | углы в радианах |
| `ground` | 1 если стоит на земле |
| `name`, `hp` | ник (игроки), здоровье (если известно) |
| `item`, `held` | `[itemId, count]` выпавший предмет, предмет в руке |

В данные не попадают: содержимое контейнеров, текст табличек, освещение, биомы, сырые метаданные сущностей.

## Сборка кадров

```bash
python3 tools/rebuild.py data/Steve_2026-11-10T12-00-00-000Z                  # информация
python3 tools/rebuild.py data/Steve_2026-11-10T12-00-00-000Z --tick 600 --out frame.npz
```

Из Python:

```python
import sys; sys.path.insert(0, "tools")
from rebuild import Recording

rec = Recording("data/Steve_2026-11-10T12-00-00-000Z")
print(rec.meta["version"]["minecraft"])

for tick, origin, blocks, entities in rec.frames(step=20):   # каждый 20-й тик
    ...   # blocks: np.uint16 [y][z][x], размер size^3; entities: список словарей
```

Кадр собирается проигрыванием записи с начала, поэтому первый вызов на поздний тик читает всё до него. Для обучения лучше идти по `frames()` одним проходом. Обрезанный файл (обрыв записи) читается до места обрыва.

## Теоретическое потребление

Размеры до gzip. Блоки хорошо сжимаются, но во сколько раз, зависит от местности. Проверь на своих записях.

### Блоки

| Что | Размер |
|---|---|
| Ключевой кадр (27–64 секции × 8 КиБ) | 216–513 КиБ один раз |
| Игрок стоит: 1 изменение блока | 19 Б (100 изменений ≈ 1,9 КБ, 1000 ≈ 19 КБ) |
| Куб сдвинулся на 1 блок | 17 Б |
| Игрок идёт: новые секции на входе в куб | около 4,5–8 КиБ на каждый пройденный блок |

Если игрок идёт всё время со скоростью 5 блоков/с, получается примерно 22–40 КиБ/с, то есть 79–141 МиБ в час. Для сравнения, полные снимки куба 48³ раз в секунду это 759 МиБ в час, а 20 раз в секунду 14,8 ГиБ в час.

### Сущности

Около 130 Б JSON на одну изменившуюся сущность за тик. Неподвижные сущности почти ничего не стоят, двигающиеся пишутся каждый тик.

| Двигающихся сущностей в кубе | За тик | В секунду (20 тиков) | В час |
|---|---|---|---|
| 10 | 1,3 КБ | 26 КБ | 91 МиБ |
| 50 | 6,5 КБ | 130 КБ | 457 МиБ |
| 200 | 26 КБ | 520 КБ | 1,8 ГиБ |

Это верхняя оценка, когда все сущности движутся постоянно.

### Оперативная память

| Где | Сколько |
|---|---|
| Состояние записи в боте | наборы ключей секций, последние JSON-строки сущностей: единицы МиБ |
| Сборка кадра в Python | до 64 секций × 8 КиБ + куб 216 КиБ: меньше 1 МиБ |
| Чанки, которые держит mineflayer | порядка сотен МиБ, зависит от view-distance сервера (оценка) |
