# CNN-DATA-BOT

Бот на Node.js (mineflayer). Заходит на ваниль-сервер, переходит в spectator, следит за игроком через `/spectate` и пишет вокруг себя в куб `size × size × size`:

- блоки (матрица ID + палитра ID → блок);
- сущности (список с ID типов + словарь ID → данные типа).

Для каждого игрока отдельные файлы. Сжатие gzip идёт в отдельном потоке (`worker_threads`). Версия Minecraft пишется в метаданные каждой записи.

## Установка и запуск

```bash
npm i mineflayer vec3 prismarine-block
node recorder.js
```

1. Бот заходит на сервер (настройки в `CFG` в начале файла).
2. Выдай ему op: `/op Recorder`.
3. Он сам делает `/gamemode spectator` и `/spectate <ник>`.

## Команды в терминале

| Команда | Что делает |
|---|---|
| `<ник>` | переключиться на игрока (текущая запись закрывается, начинается новая) |
| `list` | кто онлайн |
| `auto` | снова брать первого попавшегося |
| `quit` | корректно закрыть файлы и выйти |

Если ник не указан, бот берёт первого игрока из списка. Когда текущий игрок выходит, запись закрывается и бот переключается на следующего, для него создаётся новый набор файлов.

## Настройки (`CFG`)

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `size` | 48 | сторона куба (±size/2 вокруг бота) |
| `everyTicks` | 20 | снимок раз в N тиков (20 = 1 раз в секунду) |
| `gzipLevel` | 3 | 1 быстрее, 9 меньше файл |
| `outDir` | `data` | папка для записей |

## Выходные файлы

На каждую запись три файла:

- `ник_время.bin.gz` — блоки
- `ник_время.ent.jsonl.gz` — сущности
- `ник_время.json` — метаданные, версия, палитры

Кадры блоков и сущностей связаны номером кадра `f`.

### Метаданные (`.json`)

| Поле | Что внутри |
|---|---|
| `version` | `minecraft` (например `1.20.4`), `protocol`, `dataVersion`, `majorVersion` |
| `size`, `frames`, `startedAt`, `player` | параметры записи |
| `palette` | `stateId → { name, props }` для встреченных блоков |
| `entityTypes` | `typeId → { name, category, width, height }` для встреченных сущностей |
| `items` | `itemId → { name }` для встреченных предметов |

### Блоки (`.bin.gz`)

Кадр после распаковки:

| Поле | Тип | Размер |
|---|---|---|
| номер кадра | uint32 LE | 4 Б |
| x0, y0, z0 (угол куба) | int32 LE ×3 | 12 Б |
| блоки | uint16 LE × size³ | size³ × 2 Б |

Индекс блока: `(dy*size + dz)*size + dx`. Значение — `stateId` (учитывает состояние блока). `0` — воздух, `65535` — чанк не загружен.

### Сущности (`.ent.jsonl.gz`)

JSON Lines, одна строка на кадр:

```json
{"f":0,"t":1731260000000,"origin":[100,60,-40],"target":42,"entities":[
  {"id":42,"type":128,"pos":[124.5,84,-15.5],"vel":[0,0,0],"yaw":1.57,"pitch":0.1,"head":1.57,"ground":1,"name":"Steve","hp":20,"held":[802,1]},
  {"id":57,"type":54,"pos":[130.1,84,-12.3],"vel":[0.01,0,0.02],"yaw":3.1,"pitch":0,"head":3.1,"ground":1,"hp":20}
]}
```

| Поле | Смысл |
|---|---|
| `f` | номер кадра (совпадает с блоками) |
| `t` | время снимка, мс (Unix) |
| `origin` | угол куба, как в блоках |
| `target` | ID сущности игрока, за которым следит бот |
| `id` | ID сущности на сервере (меняется между сессиями) |
| `type` | ID типа → `entityTypes` в `.json` |
| `pos`, `vel` | позиция и скорость |
| `yaw`, `pitch`, `head` | углы в радианах |
| `ground` | 1 если стоит на земле |
| `name` | ник (только игроки) |
| `hp` | здоровье, если известно |
| `item` | `[itemId, count]` для выпавшего предмета |
| `held` | `[itemId, count]` предмет в руке, если известен |

В куб попадают сущности, чья позиция внутри него. Сам бот не пишется, а наблюдаемый игрок пишется (он есть в списке, его ID в `target`).

В данные не попадают: содержимое контейнеров, текст табличек, освещение, биомы, сырые метаданные сущностей (поза, эффекты, имя-метка и т.п.).

## Чтение в Python

```python
import gzip, json
import numpy as np

base = "data/Steve_...."
meta = json.load(open(base + ".json"))
print(meta["version"]["minecraft"])

S = meta["size"]
fb = 16 + S**3 * 2
raw = gzip.open(base + ".bin.gz", "rb").read()
n = len(raw) // fb

frames = np.empty((n, S, S, S), np.uint16)   # [кадр][y][z][x]
origins = np.empty((n, 3), np.int32)
for i in range(n):
    o = i * fb
    origins[i] = np.frombuffer(raw[o+4:o+16], np.int32)
    frames[i] = np.frombuffer(raw[o+16:o+fb], np.uint16).reshape(S, S, S)

ents = [json.loads(l) for l in gzip.open(base + ".ent.jsonl.gz", "rt")]
assert len(ents) == n
```

## Теоретическое потребление

Размер кадра блоков без сжатия: `16 + size³ × 2` байт.

| size | Блоков в кадре | Размер кадра | 1 кадр/с, час | 1 кадр/с, сутки | 20 кадров/с, час |
|---|---|---|---|---|---|
| 32 | 32 768 | 64 КиБ | 225 МиБ | 5,3 ГиБ | 4,4 ГиБ |
| **48** | **110 592** | **216 КиБ** | **759 МиБ** | **17,8 ГиБ** | **14,8 ГиБ** |
| 64 | 262 144 | 512 КиБ | 1,76 ГиБ | 41 ГиБ | 35 ГиБ |
| 96 | 884 736 | 1,69 МиБ | 5,93 ГиБ | 139 ГиБ | 119 ГиБ |

### Сущности (до сжатия)

Оценка: около 150 Б JSON на одну сущность (зависит от того, какие поля заполнены).

| Сущностей в кубе | Размер кадра | 1 кадр/с, час | 20 кадров/с, час |
|---|---|---|---|
| 10 | 1,5 КБ | 5 МиБ | 103 МиБ |
| 50 | 7,5 КБ | 26 МиБ | 515 МиБ |
| 200 | 30 КБ | 103 МиБ | 2 ГиБ |

Блоки занимают на порядки больше места, чем сущности. Оба файла сжимаются gzip, но во сколько раз, зависит от местности. Проверь на своих записях.

### Оперативная память

| Где | Сколько | Примечание |
|---|---|---|
| Буфер одного кадра блоков | равен размеру кадра (216 КиБ при 48) | создаётся на каждый снимок и передаётся воркеру без копирования |
| Строка сущностей | единицы КБ на кадр | передаётся воркеру копией |
| Очередь воркера | кадры × число кадров в очереди | растёт, только если gzip не успевает за скоростью записи |
| Палитры и словари | единицы КиБ | зависят от числа разных блоков и сущностей |
| Чанки, которые держит mineflayer | порядка сотен МиБ | оценка: зависит от версии и view-distance сервера |
| Загрузка записи в Python | кадров × size³ × 2 Б | час при 1 кадр/с и size 48 = 759 МиБ, а вместе с `raw` примерно вдвое больше |

Для обучения удобнее читать запись кусками (по кадрам из потока gzip), а не целиком.
